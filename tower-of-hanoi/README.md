# Tower of Hanoi — Recursion (Two Algorithms)

CSES "Tower of Hanoi". Read `n` (`1 ≤ n ≤ 16`), print the minimum number of
moves `2ⁿ − 1`, then each move as `from to` on peg labels `1 2 3`
(left, middle, right).

The minimum-move solution is **unique**, so both algorithms below emit the
*exact same* sequence. That is also used as a built-in correctness check.

## Topic: Recursion

This deliverable contrasts the two natural ways to express the same recursive
structure:

| Algorithm | Idea | Control mechanism |
|-----------|------|-------------------|
| **Recursive divide-and-conquer** | Solve `n` in terms of two `n−1` subproblems | The **call stack** |
| **Iterative parity rule** | Reconstruct the same sequence from a numeric/parity property | A simple **loop**, no recursion |

This is the cleanest possible "recursion vs. iteration" pairing: one *is* the
recursion, the other proves the recursion is unnecessary and rebuilds the
identical output without any call stack.

---

## Algorithm 1 — Recursive divide-and-conquer

To move `n` disks from `source` to `target` using `aux`:

1. Recursively move the top `n−1` disks `source → aux`.
2. Move disk `n` `source → target`.
3. Recursively move the `n−1` disks `aux → target`.

The recurrence is `T(n) = 2·T(n−1) + 1`, which solves to exactly
`2ⁿ − 1` moves — the proven optimum.

- **Time:** Θ(2ⁿ) — one unit of work per move, and there are `2ⁿ − 1` moves.
- **Extra space:** Θ(n) for the recursion depth (plus the output list).
- Recursion depth is at most `n = 16`, so there is **no stack-overflow risk**
  for this problem.

## Algorithm 2 — Iterative parity rule (no recursion)

The same optimal sequence is generated by a single loop over steps
`1 … 2ⁿ − 1`, using two facts:

1. **The smallest disk moves on every odd step**, always cycling in one fixed
   direction that depends only on the parity of `n`:
   - `n` even → `left → middle → right → left`
   - `n` odd  → `left → right → middle → left`
2. **On every even step there is exactly one legal move** that does not involve
   the smallest disk — so we just make it.

- **Time:** Θ(2ⁿ) — same as above.
- **Extra space:** Θ(1) of *control* state (no call stack); we keep the three
  pegs as explicit stacks only so an even step can read the two relevant top
  disks.
- No recursion → **no depth limit** regardless of how large `n` grows.

---

## Why these two

They isolate a single variable: **how the optimal sequence is produced**.
Both run in Θ(2ⁿ) time and emit byte-for-byte identical output, so any
measured difference comes purely from the control mechanism — call stack vs.
arithmetic loop — which is exactly what the "Recursion" topic is about.

### Reading the results

**1. Both are clearly Θ(2ⁿ).** From `n = 4` upward, each step of `+1` in `n`
roughly **doubles** the time for both algorithms (e.g. recursive 20.1 → 40.0 →
79.9 → 160 → 320 µs for `n = 12…16`). This is the expected exponential cost:
there are `2ⁿ − 1` moves and each algorithm does O(1) work per move.

**2. Recursion is faster across the whole range** — about **1.3× faster** once
`n` is large enough to dominate fixed overhead. The reason is per-move work:

- The **recursive** version's inner step is tiny: compare `n` against 0, two
  recursive calls, one `moves.push((from, to))`. The pegs are passed as four
  `u8` arguments in registers — no heap peg structures exist at all.
- The **iterative** version does strictly more per move: branch on step parity,
  on even steps select the two non-smallest pegs, read `pegs[a].last()` and
  `pegs[b].last()`, compare, then `pop` from one peg `Vec` and `push` to
  another. That extra bookkeeping is the ~30 % it loses by.

**3. Memory impact and caching — why the constant factors differ.** Both
algorithms stream their output into one contiguous, pre-sized `Vec<(u8,u8)>`
(`with_capacity(2ⁿ−1)`), so the *output* writes are perfectly sequential and
cache-friendly for both — that part is a wash. The difference is the **working
set** each one touches per move:

- **Recursive:** the only extra memory is the call stack, at most `n ≤ 16`
  frames. Sixteen tiny frames are a few hundred bytes — they sit permanently in
  **L1 cache** and are accessed in strict push/pop (LIFO) order, which the CPU's
  prefetcher and return-address predictor handle essentially for free. There is
  no pointer chasing and no second data structure competing for cache lines.
- **Iterative:** it keeps **three separate `Vec`s** (the pegs) on the heap.
  Across a run these `Vec`s grow and shrink, and each even step reads the *tops
  of two different pegs* — two independent heap locations whose addresses depend
  on the data so far. That's more distinct cache lines touched per move and a
  small amount of data-dependent (hard-to-predict) branching on which peg moves.
  None of it misses to main memory at these sizes (the whole peg state is only
  tens of bytes and stays in L1), but it is **more memory traffic and more
  branch-prediction pressure per move** than the recursive version's single
  sequential append. That shows up as the steady ~1.3× gap.

**4. Why the ratio is largest at tiny `n`.** At `n = 1–3` the iterative version
looks 2–2.5× slower, but that is **fixed setup cost**, not algorithmic: it
allocates three peg `Vec`s and pushes all `n` disks before the loop even starts.
With only 1–7 moves to amortise that over, the setup dominates. As `n` grows the
setup becomes negligible and the ratio settles to the true per-move difference
(~1.3×).

**5. The iterative method's real advantage is space, not speed.** It uses **no
call stack** and therefore has **no recursion-depth limit**. For Tower of Hanoi
that advantage is purely theoretical: any `n` large enough to overflow a real
call stack would require astronomically more than `2ⁿ − 1` moves than could ever
be printed. Within the CSES limit of `n ≤ 16` the recursion depth is trivially
safe.

### Bottom line

For CSES Tower of Hanoi (`n ≤ 16`), both pass comfortably within the 1.00 s /
512 MB limits — the entire `n = 16` output is only 65 535 moves, generated in
well under a millisecond. **The recursive solution is the better practical choice
here:** shorter code, ~1.3× faster, and more cache-friendly (one hot L1 call
stack + a sequential output append, versus the iterative version's three heap
peg `Vec`s and extra per-move memory traffic). The iterative solution wins only
on the metric this problem never stresses — bounded, recursion-free stack
usage.

## Build & run

```bash
# Run a solution (reads n from stdin)
echo 2 | cargo run --release --bin recursive
echo 2 | cargo run --release --bin iterative

# Correctness tests: example, both-agree for n=1..16, every move legal
cargo test --release

# Benchmark
cargo bench
```

> **Note on output speed:** both binaries write through a `BufWriter`. With up
> to 65 535 lines, an unbuffered `println!` per move is the usual cause of a
> TLE on this problem; buffering keeps it in microseconds.

## CSES checklist

- ✅ Prints `2ⁿ − 1` first, then the moves.
- ✅ Move format `a b` on peg labels `1/2/3`.
- ✅ Matches the sample (`n = 2` → `3` / `1 2` / `1 3` / `2 3`).
- ✅ Within time/memory: `n = 16` is ~65 k lines, generated in well under a ms.
- ✅ Buffered output to avoid TLE.
